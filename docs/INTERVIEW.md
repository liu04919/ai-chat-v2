# 简历与面试准备

定位：前端开发 / AI 应用前端，以流式交互和状态管理为主线，后端与部署作为工程能力补充。以下是候选文案，不代表商业上线规模；只保留自己能独立解释的条目。

## 简历项目经历

### AI Chat｜全栈 AI 对话应用

**技术栈：** Next.js、React、TypeScript、AI SDK、TanStack Query / Virtual、Zustand、PostgreSQL、Redis / BullMQ、Drizzle、R2。

**项目简介：** 面向个人学习的 AI 对话应用，支持流式聊天、断线续传、Agentic RAG、联网与 MCP 工具、文件直传、图片生成及会话分享；采用独立 Worker 执行生成任务，并部署至云服务器。

- **流式恢复与状态管理：** 拆分持久化消息与 Generation 执行状态，基于 Redis Streams / SSE 实现事件回放；通过 Zustand 缓存输出投影与游标，结合服务端对账、事件去重和最近访问淘汰，处理会话切换、刷新及停止后的展示衔接。
- **长对话渲染优化：** 服务端合并相邻文本增量，客户端使用 requestAnimationFrame 批量提交流事件；结合游标分页与动态高度虚拟列表，减少高频状态更新和长历史挂载，并处理历史追加锚定、图片测量与底部跟随。
- **知识库与工具交互：** 实现预签名 URL 文件直传、异步解析入库及引用快照展示；将知识库检索与联网、MCP 接入统一工具流程，使用 PostgreSQL 向量检索、BM25、RRF 与精排提供检索结果。
- **工程完整性：** 补充运行时契约校验、数据库/队列集成测试和跨标签页账户切换清理；通过 GitHub Actions 完成检查及手动触发的源码发布，使用 Docker Compose 与 Caddy 部署 Web / Worker。

投递时保留四条即可；版面紧张先压缩技术栈和最后一条。不要再叠加 V1 的全部功能描述或未经本版验证的性能百分比。

## 开场介绍

### 30 秒版

这是一个我用来学习 AI 应用工程的全栈聊天项目。我重点做的不是简单把模型输出显示出来，而是处理生成过程中切换会话、刷新、停止和失败时的状态一致性。后端把执行交给独立 Worker，前端分开管理持久化历史与实时投影，同时用增量合并、按帧更新和虚拟列表控制渲染成本。另外也接通了知识库工具、文件直传和云服务器发布。

### 两分钟展开顺序

先演示“生成一半切走再回来”，再讲四个问题：生成为什么没有停止；回来从哪个游标继续；如何避免重复拼字；生成结束后谁替代流式状态。最后展示一段引用和对应原文，说明 AI 功能也有明确的授权、持久化与失败边界。不要用两分钟罗列十几个库名。

## 高频追问与回答要点

### 1. 为什么不直接在 Next.js 请求里调用模型？

希望生成任务不依附某个浏览器连接。Web 负责认证、命令与事件转发，Worker 持续执行模型和工具。断开连接不等于取消生成。代价是增加队列、事件日志及跨系统失败边界，并不是所有聊天应用都必须这样拆。

追问“数据库写完、入队失败怎么办”：当前返回明确的 503，保留 queued 记录；相同命令幂等返回原任务并重试入队。Job ID 使用 generationId。没有跨 PostgreSQL / Redis 原子提交，也不能声称故障后一定自动恢复。见 [create.ts](../apps/web/src/server/generations/create.ts)。

### 2. TanStack Query 和 Zustand 为什么都用？

Query 保存可重新获取的服务端数据，比如历史页、详情和知识库列表；Zustand 保存尚未被持久化历史接管的生成投影和游标。组件局部状态负责交互。切走时保留流式投影才有增量续传的意义，但要有容量上限和账户切换清理，不能无限积累。

### 3. 有 Last-Event-ID 就够了吗？

不够。游标代表“已应用到哪个事件”，必须与累计内容一致。若先存游标，尚未执行 rAF 就卸载，回来会跳过那批内容。现在内容和游标同批提交；同一连接重连用 Header，新连接用缓存游标，服务端以 Header 优先。整页刷新无内存缓存，要重新回放活跃任务，而非仅保存一个孤立 ID。

### 4. 为什么做两层合并？会不会拖慢首字？

Worker 合并减少事件写入与传输频率；浏览器按帧合并减少状态提交频率，解决的层次不同。当前 Worker 首个有效增量直出，后续默认按 40 ms / 128 字符策略合并；不跨不同 part 或工具事件合并。合并会牺牲部分中间更新的即时性，不能承诺任何机器都严格 40 ms。见 [delta-coalescer.ts](../apps/worker/src/generation/delta-coalescer.ts)。

### 5. 优化效果的数字从哪来？

当前这份简历只陈述机制，不填写缺少证据的比例。若使用独立最小实验的数据，应注明它不是完整业务页面：固定同一份流数据、节奏、Markdown 内容、浏览器和构建模式，对照有无两项优化。

React Profiler 的 Commit 次数、渲染耗时与自己记录的 store 更新次数分开统计；浏览器 Performance 看主线程任务、脚本/布局绘制耗时、长任务及交互情况。首可见内容延迟也要保留，防止用明显延迟换取更少更新。重复多轮报告中位数和范围，不只选最好的一次。V1 的百分比不能直接迁移到 V2。

### 6. 虚拟列表为什么还要分页？

虚拟化只减少屏幕外 DOM 挂载，不会自动减少数据库读取和客户端数据量。分页控制获取范围；动态高度测量适应 Markdown、图片与思考展开；插入更早历史要保持阅读锚点，新输出只在用户原本位于底部时跟随。见 [virtual-message-list.tsx](../apps/web/src/components/chat/messages/virtual-message-list.tsx)。

### 7. Agentic RAG 与普通 RAG 有什么区别？

传统版先固定检索一次再生成；当前模型通过工具选择是否检索、改写查询或补搜。检索工具内部仍使用确定的混合检索和精排流程。授权范围由服务端绑定，不能让模型随便传 ownerId。最多三次检索是预算保护，不等于质量保证。

不要说“Agentic 必然更好”：已有[短事实问答对照](../evals/rag/reports/agentic-v1/agentic-fixed/findings.md)没有证明正确性提高，额外调用增加了延迟，忠实度评分还下降。这个结果说明要区分任务适配与功能复杂度，而不是隐藏负面结果。

### 8. 800/100、30、6 是最优参数吗？

不是。800/100 是 UTF-16 字符规模和重叠预算，不是 token；30 是每路召回数，6 是单次精排保留数。已有[有限网格实验](../evals/rag/reports/cmrc2018-v1/report.md)，但短文样本没有区分出更好的配置，因此保留默认值，不能推广为所有知识库最优。面试主线不必背检索指标，先讲清这些参数作用在哪一层。

### 9. 摘要会不会丢掉历史？

模型上下文会损失细节，数据库原始消息不会被覆盖。较早的完整轮次进入滚动摘要，保留近期原文和当前问题；保存摘要时复核版本与取消状态。文本计数预计算并保存，附件按内容生成缓存；这些仍是估算，不等于供应商账单。见 [上下文准备](../apps/worker/src/context/prepare-chat-context.ts)。

### 10. 文件直传和引用如何控制权限？

后端先校验用户并签发短期上传 URL，浏览器直接 PUT 对象存储，再由完成接口核验对象元数据。读取文件仍需鉴权；模型检索使用服务端确定的账户/知识库范围。引用以回答快照保存，所以源文件删除后旧回答仍能看引用；删除原文件不等于撤销已分享内容，需要另行撤销分享。

### 11. 怎么防止两个标签页同时发送？

前端禁用按钮只是体验。服务端通过会话锁、相同 userMessageId 的幂等校验和数据库活跃任务唯一约束处理竞争。校验失败需真正回滚，不能在事务中插入会话后正常 return 错误对象，否则会留下空会话。见 [command.ts](../packages/db/src/generations/command.ts)。

### 12. 部署是真正 CI/CD 吗？

有 CI 检查和可重复的发布工作流，但需要准确描述：push main 运行 CI，手动触发 Deploy 后检查同一提交并上传源码，服务器构建、迁移、启动并检查健康。不是镜像构建一次到处发布，不是零停机，也不会自动回滚数据库。当前服务通过 SSH 隧道供个人访问。见 [CI/CD](../deploy/CI_CD.md)。

## 准备材料时的底线

- 不写“高并发”“生产级高可用”“零丢失”“杜绝幻觉”或没有对照记录的性能提升。
- 公开语料成绩不是自己的真实用户业务数据，旧传统版成绩不是当前 Agentic 成绩；单次渠道响应速度不是系统 SLA。
- 若被问到 AI 辅助开发，如实说明使用方式，并准备讲清自己读懂、验证和调整过的设计；不能把生成代码量包装为个人工程经验。
- 可以打开旁边的正式测试解释边界，但测试数量不等于覆盖率。面试前先练熟上面第 2–6 题，再扩展 RAG、事务与部署。
